# Veritas 评测设计 v1

> 本文件是 Veritas 的评测基准文档：用什么样例、按什么标准、由谁判分。
> **权威是 `docs/design-guide.md`（产品真相源）**：样例的预期输出对齐文档规格，不对齐当前代码实现——代码落后于文档时，以文档为准，差距是待修的代码。
> 产品规格看 `docs/design-guide.md`，代码导航看 `docs/project-map.md`，本文件不复述这两者。
> 最后对照 design-guide：2026-05-31（v3.2）

## 0. 判官与范围（先说清，避免悬空）

- **判官 = 人工打分。** v1 不用 LLM-as-judge，也不跑自动断言。我（产品）按下文 rubric 逐条人工评分，结果记入 `results.csv`。
- **为什么人工起步**：评测对象本身是 LLM，再用 LLM 当判官会循环论证；起步阶段人工最可信，待样例稳定后再考虑自动化。
- **v1 范围**：本文档的评测设计 + 3 条黄金样例 + `results.csv`（先放表头，真实跑完再填）。不含自动化测试。

## 1. 评测维度

评估三个 Agent 是否按 design-guide 定义稳定工作：

- **Agent 1 节点分析师（design-guide §5）**：抽出的节点是否有诊断价值、是否忠于原文。
- **Agent 2 分层家教（design-guide §6/§8）**：是否按认知层级准确判断真实掌握程度，追问是否切中要害。
- **Agent 3 报告生成（design-guide §9）**：是否基于用户真实原话生成可信报告，盲点定位是否准确，建议是否可执行。

## 2. 规格契约（样例必须对齐 design-guide，否则就是假 eval）

每条样例的"预期输出"只能用 design-guide 规定的产物，**区分"语义判断（Agent 输出）"和"确定性状态（代码维护）"**：

**Agent 1 节点输出（design-guide §5）**：稳定 id、节点名称、一句话说明、材料证据片段、优先级理由
> 注意：节点**没有"适用层级"字段**。所有节点统一走记忆→理解→应用→分析四层（§5/§6），层级不由 Agent 1 决定。

**Agent 2 输出（design-guide §8）**：自然对话回复 + 结构化状态，结构化状态**只含两项**：① 当前层级是否通过（语义判断）② 当前盲点摘要。
> 注意（§8/§104）：下一步动作（继续当前层 / 进入下一层 / 完成节点）、提示/答案使用记录，都是**确定性状态、由代码维护，Agent 2 不上报**。故样例的 Agent 2 预期输出不写 nextAction、不写 supportUsed。

**确定性状态（代码维护，非 Agent 输出，§7/§8）**：
- 提示/答案使用：只由用户点"给我提示 / 给我答案"按钮触发，代码记录。
- 层级推进、score：代码维护。

**Agent 3 报告输出（design-guide §9）**：每节点含——层级通过情况、用户原话证据（不编造）、具体盲点、是否使用提示/答案、正确理解、下一步建议。
> 层级状态取值（§10 旁注栏）：已通过 / 进行中 / 未通过 / 答案辅助 / 未开始。

**评分规则（design-guide §7，代码维护，非 Agent 判断）**：每节点满分 100，四层各 25；独立通过 25、提示后通过 25、答案辅助 0。分数是辅助摘要，不是核心结论。

认知层级与通过标准（§6）：记忆（识别/定义）→ 理解（自己的话解释）→ 应用（放进场景并说明怎么用）→ 分析（拆机制/因果/边界/对比）。
不算通过（§6）：只堆关键词、答非所问、逻辑矛盾、场景与概念无关、看答案后才答对。

## 3. 评分标准（1–5）

### Agent 1
| 分 | 标准 | 例子 |
|---|---|---|
| 1 | 偏离材料，或无诊断价值 | 材料讲 RAG，却抽出"人工智能发展历史" |
| 2 | 来自材料，但只是泛泛总结 | 节点"RAG"，说明"RAG 是一种 AI 技术"，只能问定义 |
| 3 | 节点合理，可支持基础追问 | 节点"RAG 的基本流程：先检索文档，再基于文档生成回答" |
| 4 | 有诊断价值，能暴露常见误区 | 节点"RAG 中检索与生成的职责分工"，能查是否混淆检索与生成 |
| 5 | 高诊断价值，且明确服务后续层级诊断 | 节点"RAG 不是让模型记住资料，而是在回答时引入外部证据"，能诊断"训练记忆误解""只会堆关键词""不会判断适用场景" |

### Agent 2
| 分 | 标准 | 例子 |
|---|---|---|
| 1 | 明显误判，破坏层级诊断 | 用户答"有检索、有生成、有上下文"，Agent 直接判理解通过 |
| 2 | 没误判，但反馈泛泛 | 只说"回答不完整，再详细说说"，不指出问题 |
| 3 | 能识别未通过，并给出基础追问 | 追问"检索到的资料对模型回答有什么作用？" |
| 4 | 能指出具体盲点，并围绕材料继续诊断 | 指出用户在堆关键词，要求解释"外部证据如何约束生成" |
| 5 | 判断准确，并按错误类型动态追问 | 判理解层未通过，用反例追问"如果没检索到资料，幻觉风险为什么升高？" |

### Agent 3
| 分 | 标准 | 例子 |
|---|---|---|
| 1 | 空泛总结，或编造用户没说过的话 | 写"用户已掌握 RAG"，但无原话证据 |
| 2 | 有结论，但证据弱 | 写"应用能力需加强"，但不说明哪句话暴露问题 |
| 3 | 能写出层级结果和主要问题 | 说明"理解层不稳定，应用层边界不清"，但引用不足 |
| 4 | 有真实原话和具体盲点 | 引用"只要是问答系统都应该用 RAG"，指出其泛化错误 |
| 5 | 证据、层级、盲点、建议完整闭环 | 含层级通过情况、用户原话、具体盲点、正确理解、下一步练习 |

## 4. 黄金样例（v1：3 条）

### 样例 1 — 高频正常路径（理解层堆关键词，未通过）

**材料**
> RAG 会先检索相关文档片段，再把这些片段作为上下文交给大模型生成回答。它的目的不是让模型记住更多知识，而是在回答时引入外部证据，降低幻觉。

**预期 Agent 1 节点**
- `name`：RAG 中检索与生成的职责分工
- `context`：用户容易把 RAG 误解为"让模型记住知识"，该节点能暴露概念边界
- `sourceExcerpt`：RAG 会先检索相关文档片段，再把这些片段作为上下文交给大模型生成回答
- `priorityReason`：能区分用户是否混淆"检索取证"与"训练记忆"

**模拟对话**（当前层级 understanding）
- Agent：为什么 RAG 不是让模型记住更多知识，而是能降低幻觉？
- 用户：因为它有检索、有生成、有上下文，所以更准。

**预期 Agent 2 输出**（语义判断，§8）
- 当前层级（understanding）是否通过：否
- 当前盲点摘要：只堆关键词，没解释外部证据如何约束生成

**代码维护状态**（非 Agent 输出）：未点提示/答案按钮。

**预期 Agent 3（若到此结束）**
- 层级通过情况：记忆=已通过，理解=进行中，应用=未开始，分析=未开始
- 用户原话证据："因为它有检索、有生成、有上下文，所以更准。"
- 具体盲点：能说出关键词，但未解释检索到的证据如何减少凭空编造
- 正确理解：RAG 在回答时检索相关证据，让模型基于证据生成，而非记住资料

**代码派生分**（design-guide §7，代码维护，非 Agent 输出：独立通过/提示后通过 25，答案辅助 0）
- 本样例 = 25（仅记忆独立通过）

**禁止错误**
- 不能判 understanding 通过
- 不能写"用户已掌握 RAG 原理"
- 不能引入材料没提到的 embedding、向量数据库调优

### 样例 2 — 边界路径（答非所问 / 非知识作答）

**材料**：同样例 1。

**模拟对话**（当前层级 memory）
- Agent：RAG 在这份材料里大致分成哪两个动作？
- 用户：这玩意儿太难了，能不能直接告诉我答案，别问了。

**预期 Agent 2 输出**（语义判断，§8）
- 当前层级（memory）是否通过：否
- 当前盲点摘要：用户未作答，无法判断掌握程度
> 依据 design-guide §8：用户在抱怨/求助、不是知识作答时，需自然承接再拉回，不当作知识作答来判层级。

**禁止错误**
- 不能把抱怨当成回答去判 memory 通过或不通过的"知识结论"
- 不能把"想要答案"改写成"用户没准备好回答"这类话术
- 不能直接跳过该层

### 样例 3 — 高风险路径（看答案后误判 + 报告伪造）

**材料**：同样例 1。

**模拟对话**（当前层级 application）
- Agent：如果做公司内部制度问答助手，什么时候适合用 RAG？
- 用户：不知道。
- 请求类型：answer
- Agent：给出答案……
- 用户：哦，那就是制度更新快的时候用。

**代码维护状态**（非 Agent 输出，§7/§8）：用户点了"给我答案"，代码记录答案使用，应用层标记为"答案辅助"，不算独立通过。

**预期 Agent 2 输出**（语义判断，§8）
- 当前层级（application）是否通过：否（看答案后复述，依据 §6"看答案后才答对不算通过"）
- 当前盲点摘要：在给出答案后才复述，应用层未独立掌握

**预期 Agent 3**
- 层级通过情况：应用=答案辅助（不是已通过）
- 是否使用答案：是
- 用户原话证据：只能引用用户真实说过的话
- 具体盲点：应用层依赖答案提示，独立判断适用场景的能力未验证

**禁止错误**
- 不能因为复述了答案就判 application 通过
- 报告不能伪造用户原话（只能引用真实对话）
- 报告不能引入材料外概念

## 5. 候选扩展样例（v2 再补，不在 v1 主表占位）

- 低频但重要：材料很短，节点不适合推进到 application/analysis
- 长材料：节点数量上限（最多 8 个）的截断行为
- 分析层正常通过路径：用户能拆出机制/边界/对比
- 多节点切换：`complete_node` 后进入下一节点
- 其他高频材料：提示词工程、React 状态、数据库索引、MCMC

## 7. Badcase 台账模板（结构化回流）

每个 badcase 一条，强制结构化，便于回归：

```
Badcase ID：A2-LEVEL-004
材料：RAG 会先检索文档片段，再交给模型生成回答
用户回答：RAG 就是让模型提前学会这些资料
实际输出：Agent 判定 understanding 通过
期望输出：不通过，轻量纠正"提前学会"和"检索时引用"不同
问题类型：层级误判 + 事实性错误处理不足
根因：prompt 对"训练记忆"和"检索引用"的混淆没有明确反例
修复方式：在 Agent 2 prompt 加入该类误区处理；新增 questioner 测试
回归状态：已加入 tests/lib/questioner.test.ts
```

归因分类：a) prompt 规则不清 b) 解析/字段校验不足 c) 状态机推进错误 d) 评测集没覆盖 e) 产品定义不清
