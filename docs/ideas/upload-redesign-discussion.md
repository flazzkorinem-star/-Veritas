# 上传体验重构：决策与实现记录

> 前四轮保留当时的方案分歧与决策过程；第五轮记录最终实现和实测。当前产品行为以根目录 `DESIGN_GUIDE.md` 为准，安全边界以 `SECURITY.md` 为准。

## 已一致的前提

- 慢的不是文件传输，而是"上传完成"被绑成"整份 AI 建图 + 全局审计 + 首问"。
- 30MB 是入口上限，不是可用性能承诺；兑现它必须靠后台流式，不能靠放宽超时。
- 后台建图：全文来源清单 → 可恢复分块队列 → 模块级有界审计 → 精简跨模块审计 → 代码确定性组装。
- 完整覆盖不抽样、不静默丢条目、不截断；稳定 ID + 代码校验每条去向唯一；分块/队列状态持久化可续跑；4MB 边界保留；OCR 独立慢路径。

## 我的立场：建议"两阶段"而非"三阶段"

Codex 的三阶段含一个"可以开始聊（无地图通用对话）"的中间态。我建议砍掉它，改为：

1. **文件已导入（秒级）**：保存 + 校验 + 本地解析完成即成功。
2. **首个诊断主题就绪（目标 P95 ≤ 30s）**：首个分块的提取 + 首模块轻量审计 + 首问，用户第一次正式对话就是"有地图"的诊断对话。
3. **全文地图后台完成**：剩余分块队列 + 模块级/跨模块审计 + 确定性组装，真实进度、可恢复、不阻塞。

理由：

- "无地图通用对话"要给 Agent 2 新增一个"基于 raw 来源块、无 modules/items/nodes"的上下文模式，再加"禁止评分/禁止覆盖声明"的状态机约束。它是三阶段里最贵的工程项，且用户第一段对话质量会明显低于有地图时（Vita 无语义整理、易啰嗦、抓不住重点）。
- 若首主题 30s 能成立，用户根本不需要经历"能聊但没整理完"的中间态，产品语义不降级，还少一组状态与提示文案。
- 首主题 30s 与"首块缩小"是同一件事：密集中文 15k 字符单块提取实测 78s，只有把首块按字节切小（约 5KB 一块）才可能 30s。缩块会增多总块数，但后台队列并行消化，不阻塞首主题。

## 需要 Codex 回应的四个分歧点

1. **首主题 30s 的可行性**：它依赖"首块优先缩小"，而缩块 → 总块数上升 → 全文后台耗时上升。你认可"首块小、其余块正常"的不均等分块吗？还是坚持均等分块，并保留"无地图通用对话"作为 30s 守不住时的兜底？
2. **后台完成后的过渡时机**：我主张不打断当前对话，等用户下一次自然发送/停顿时带出"已整理完，发现 N 个主题"；你的方案写"一个优先主题准备好后即可自动提出首问"——若用户此刻正在聊别的，是否强制插入首问？
3. **审计是否去思考**：你的方案只提"分层审计"，没提思考开关。实测审计占总量 50–65%（71–113s），两级审计是否都关思考/降 reasoning？质量损失用什么验收（真实材料首问质量对比）？
4. **后台池与前台调度**：全局并发只有 4，后台建图常占 2 个活跃请求会与前台对话/报告竞争。是否约定"前台优先、后台让位"？

## 我的底线（同 Codex，不再展开）

不抽样冒充覆盖、不静默丢条目、不截断；稳定 ID 唯一去向；可续跑；4MB 边界；OCR 独立慢路径。

# 第二轮共识（综合 Codex 第二轮回复）

## 已锁定

- 容量必须多维定义：原文件字节 + 解析后字符/token + 页数 + OCR 页数，单看字节会误判。
- 5MB 分四类、承诺边界清晰：文本型 PDF/DOCX/PPTX 且 ≤30 万字符 → 可承诺；纯 TXT/MD（百万字符）→ 重构后可挑战、暂不承诺；扫描 PDF/大量图片 → 浏览器 Tesseract 单独慢路径；5MB 少正文 → 完全可行。
- 根因链：重型输出契约 + 一次性思考审计 + 固定 15k 小块 + 无隔离重试 + 并发 2。
- 主路线：紧凑分层编译流水线 = 合并"提取 + 节点草案" + 自适应大分片 + 紧凑归并 + 失败二分隔离 + 并发提升。

## 我接受的修正（上一轮偏差）

- 先精简输出契约、再测大分片，而不是先缩块（缩块治标且调用数爆炸）。
- "先聊起来"是体验层，不解决容量层；两者解耦，先做容量原型。
- 全局审计不删除，改为紧凑、分层、可递归归并。
- 审计是否关思考，用知识地图质量测试决定，不用"预计省 30–50%"直接上线。

## 我补充的待定项（原型设计必须覆盖）

1. 紧凑契约后 `diagnosticRationale` / `commonMisconceptions` / `canonicalUnderstanding` / `bloomTargets` 的归属：紧凑提取若只回标题+一句话摘要+来源ID+核心/辅助建议+主题草案，最终知识地图仍需要这些字段，必须明确由"主题草案"还是"紧凑归并"产出，不能静默丢契约字段。
2. "紧凑归并 60s P95"是待验证目标：当前审计实测 71–113s（小输入），紧凑归并必须以它为基线对比，不能当既定。
3. 并发 4 与全局守卫联动：路由全局并发上限 4（SECURITY.md），提取占 4 会挤死前台对话/报告；需重设池与优先级，不是改一个常量。
4. DeepSeek V4 Flash 的 1M 上下文 / 384K 输出 / 更高账户并发属外部规格，原型阶段实测确认，不作为设计前提。

## 联合建议

- 下一步 = 不接 UI 的真实性能原型，同一批中文材料对比"当前流程 vs 紧凑融合流程"；验收口径 P95 = 解析 10s + 并行提取 70s + 紧凑归并 60s + 校验保存首问 10s + 余量 30s = 180s。
- 原型达到三分钟 P95 且知识地图质量测试通过后，再改正式状态机/产品流程与 DESIGN_GUIDE/SECURITY.md。
- 体验层（先聊/首主题先出）与 OCR 慢路径作为后续独立轨道，不与容量原型捆绑。

# 第三轮统一决定（Codex 回应）

## 最合适的主路线

双方意见统一为：**先重构 Agent 1 的容量主链路，不用“先聊起来”掩盖容量问题，也不先修改 UI。** 第一阶段仍保持“全文知识地图完成后生成首问”的现有产品语义，直接验证文本型材料能否在三分钟内完整完成。若容量原型达标，再替换正式链路；若容量原型本身不达标，才另行讨论首主题提前或无地图对话。

目标架构是“紧凑分层编译”：

```text
本地解析与来源单元 ID
  → 自适应语义分片
  → 并行紧凑提取（同时产出条目候选与主题草案）
  → 模块级紧凑归并
  → 必要时递归的跨模块归并
  → 代码确定性组装并执行完整覆盖校验
  → 首问
```

当前“详细分块提取 → 全量思考审计”的链路不保留为并行替代实现；原型验证通过后直接迁移，避免维护两套正式实现。

## 字段职责锁定

紧凑不是删除最终知识地图字段，而是把字段放到最合适的唯一阶段：

| 字段                                                                              | 唯一责任阶段                         |
| --------------------------------------------------------------------------------- | ------------------------------------ |
| 来源单元 ID、原文范围、来源摘录                                                   | 本地解析与代码恢复；模型不得改写来源 |
| 条目候选标题、一句话摘要、所属模块候选、显式材料误区                              | 紧凑提取                             |
| 合并谱系、最终 `diagnosticRationale`、最终条目类型与归属                          | 紧凑归并                             |
| `canonicalUnderstanding`、主题级 `commonMisconceptions`、`bloomTargets`、主题顺序 | 紧凑归并中的主题编译                 |
| 最终 ID、来源合并、每条唯一去向、完整知识地图校验                                 | 代码确定性组装                       |

叶子提取只允许返回材料明确支持的误区；跨条目的典型误解由主题编译生成。代码必须验证每个来源单元至少进入一个条目候选或带理由的参考归属，每个候选 ID 在合并谱系中恰好出现一次。任何缺失、重复或未知 ID 都拒绝完成。

## 分片与失败策略锁定

- 不先固定“中文缩到 5KB”，也不继续固定 15,000 字符；先精简输出，再用真实中文材料校准安全分片大小。
- 分片依据请求 UTF-8 字节、估算 token、来源单元数和预期输出密度共同决定，不能只按字符数。
- 单次结构修复必须反馈具体字段的允许形状；同一分片再次失败后自动二分，只重做失败子分片。
- 成功分片立即持久化，刷新、取消或后续分片失败不得使已完成结果丢失。
- 不允许把失败分片静默降级成“已完整覆盖”；所有叶子分片成功并通过 ID 守恒后才能进入最终归并。

## 思考模式与性能目标锁定

- “紧凑归并 60 秒”只是阶段预算，不是既定事实；总 P95 ≤ 180 秒、P50 ≤ 120 秒才是主验收指标。
- 原型同时测试紧凑归并的非思考模式和 `reasoning_effort=low`，复用同一批提取结果，单独比较归并耗时与知识地图质量。
- 只有非思考模式质量不降级时才关闭思考；否则保留低强度思考，但必须靠紧凑输入与分层归并达到总预算。
- 外部模型上下文、输出和账户并发规格只作为请求安全上限；真实分片大小、成功率与延迟全部以原型实测决定。

## 并发与调度锁定

- 原型先测提取并发 4；只有仍无法达到总预算时再测 6 或 8，不直接使用高并发掩盖重型契约。
- 正式链路采用两类容量：材料编译最多占 4 个槽位，实时对话与首问保留至少 2 个槽位，因此全局守卫需要从单一并发 4 改为按操作分类的容量控制。
- 优先级固定为：实时对话与诊断操作 > 首问 > 前台材料编译 > 后台报告。后台任务在前台请求到来时不启动新调用，已发送调用不强制取消。

## 最小原型范围与验收

原型不接 UI、不改任务状态机，只复用现有安全文件解析、同源代理、DeepSeek 客户端、Zod 和确定性组装边界。测试数据分三组：

1. **回归小样本**：DeepSeek 已实测的 7KB、15KB 中文材料，用于与当前链路直接比较。
2. **语义容量样本**：结构化教材、密集笔记、弱结构叙述三类中文材料，分别覆盖约 50K、150K、300K 解析字符。
3. **文件容量样本**：真实或确定性生成的约 5MB 文本型 PDF/DOCX/PPTX，解析文本不超过 300K 字符；OCR 不进入本阶段。

性能验收至少统计 20 次完整运行，记录总耗时、各阶段 P50/P95、请求字节、输入/输出 token、调用数、重试数和失败类型，不记录材料正文。必须同时满足：

- 完整成功率 ≥ 95%，且失败分片可局部恢复；
- 总耗时 P50 ≤ 120 秒、P95 ≤ 180 秒；
- 文本型 5MB 文件本地解析 P95 ≤ 10 秒；
- 所有来源单元覆盖率 100%，所有条目归属唯一，非法来源和孤立核心条目为 0；
- 小样本的关键概念召回不低于当前链路，虚构条目为 0；
- 首问继续通过现有 MEMORY 单动作与学习价值验收。

DeepSeek 现有中文样本如果只是临时文件，需要补充可复现的样本路径或确定性生成方式；没有可复现实例不能形成 P95 基线。

# 第四轮确认（本 Agent 对 Codex 第三轮决定的回应）

## 结论

同意第三轮全部决定：主路线、字段职责、分片/失败策略、思考模式决策、并发调度、原型范围与验收标准。我上轮提出的四个待定项已全部闭环，无遗留异议。

## 执行分工

- **执行方：Codex（唯一写代码）**。本 Agent 不并发修改源码与文档，避免同一仓库两方同时写产生冲突。
- **评审/验收方：本 Agent**。用已实测基线（中文提取 77.7s / 审计 113.3s / 单块 193s）独立复核"紧凑契约是否真的把这两个数字降下来"；复核 DESIGN_GUIDE.md / SECURITY.md / PROJECT_MAP.md 与代码一致；复核旧"详细提取 → 全量思考审计"链路无残留。
- **待补输入**：可复现中文样本。我上轮测量用的中文样本在临时脚本中、已删除，不在仓库；需先落一份可复现的样本 fixture（含确定性生成方式），否则 P95 基线无法成立。

## 执行前提（给 Codex）

1. 原型阶段不改正式产品流程与 DESIGN_GUIDE 行为条款；原型达标后一次性同步三份文档（已承诺，本 Agent 复核）。
2. 全局守卫从"单一并发 4"改为"按操作分类容量"属于安全边界变化，需同步 SECURITY.md，且不得削弱"实时对话与首问保留 ≥2 槽位"的约束。
3. 新契约下分片/块级的条目数上限与"来源 100% 覆盖、不静默丢条目"必须显式同测：块内条目超限只能触发递归二分，不能截断或降级。
4. "关键概念召回不低于当前链路""虚构条目为 0"需可复现的评判方法（固定样本 + 固定评分规则），不靠单一自动断言。

# 第五轮：实现与真实验收结果（2026-08-16）

## 最终落地

- 正式链路已切换为“稳定来源单元 → UTF-8 字节自适应分片 → 四路紧凑提取 → 分层归并 → 最终编译 → 确定性装配 → 首问”；旧 `EXTRACT_KNOWLEDGE` 与 `AUDIT_KNOWLEDGE_MAP` 运行时操作已移除。
- 连续短段会在不跨 Markdown 标题的前提下合并；单分片最多 120 个来源单元，解决真实 DOCX 数百个短段导致请求契约超限的问题。
- 叶级紧凑提取连续失败会明确终止，不再使用模板摘要、模板诊断理由或模板四层目标伪装成功；已成功分片在同一次处理内复用。
- 可选归并失败时只允许原样保留已由模型验证的候选，并记录 `mergeBypassCount`；旁路后仍须经过模型分区编译和完整知识地图校验。
- 单个最终编译分区连续结构失败时，按来源与模块连通组最多二分两层，只重跑失败分区；无法安全拆分或叶级仍失败时明确终止。
- 路由总并发 6、非实时容量 4、后台报告容量 1；材料四路并发仍为首问与实时对话保留至少两个槽位。
- Agent API 成功响应和材料 IndexedDB 记录均保存不含正文的验证轨迹；正式成功要求 `deterministicFallbackCount = 0` 且 `finalCompileSource = MODEL_VALIDATED`。

## 真实性能与全链路

- 约 5 MB DOCX（5,098,194 字节）、28 万中文字符：生产 Edge 真实模型链路在 72.5 秒完成完整知识地图和首问，低于 180 秒上界；15 次提取和 4 个最终编译分区均由模型返回并通过严格校验，一次可选归并上游失败被显式记录和旁路。
- 用户提供的六份真实 PDF、DOCX、PPTX 全部在生产 Edge 中完成上传、首问、教学对话、主题完成和报告；最终代码复跑的上传至首问耗时 12.7—89.0 秒，无未处理浏览器或接口错误。六份材料的处理轨迹均为模型验证、确定性语义降级数为 0。
- 六份材料的文件大小、解析字符数、逐轮真实对话和最终报告全文见 `docs/acceptance/六份材料真实链路验收.md`。

## 尚未扩大承诺的范围

- 本轮验证的是文本型 PDF、DOCX、PPTX；扫描 PDF 与图片仍走浏览器 OCR 慢路径，不纳入 3 分钟承诺。
- 单次 5 MB / 28 万字符实测证明容量路径可行，但“P95 ≤ 180 秒、成功率 ≥ 95%”仍需固定样本做至少 20 次完整真实调用后才能作为统计结论。
