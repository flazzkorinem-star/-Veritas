# 上传慢与材料大小上限的诊断

> 2026-08 现场调查结论（含真实 DeepSeek 实测数据）。本文只记录现状、根因与候选方向；最终方案待用户拍板后另立文档。

## Problem Statement

1. 上传一份材料要等好几分钟，体验很差。
2. 实际只有约 10KB 的小文件能走完，稍大的文件会一直处理到超时失败。

## 现状：上传到底在做什么

"上传"没有网络传输（全部本地 IndexedDB），耗时全部来自**同步完成整份材料的模型处理**。流程（`src/features/materials/process-text-material.ts` 编排）：

1. **读取与解析**：`material-file.ts` 校验 30MB 上限、扩展名/MIME/签名/ZIP 结构；`parse-material.ts` 按格式分派（TXT/MD 直接解码、DOCX Mammoth、PPTX JSZip、PDF 逐页 PDF.js、无字页渲染后 Tesseract OCR）。本地毫秒级（OCR 除外，见下）。
2. **分块**：`chunk-source-blocks.ts` 把解析文本按来源块聚合成 ≤15,000 字符的分块（30 万字符上限 → 最多 20 块）。
3. **分块提取**：每块一次 `EXTRACT_KNOWLEDGE` 上游调用（非思考、输出上限 12,000 token、单操作总超时 90 秒含重试），固定 2 路并行、按原文顺序推进（`EXTRACTION_CONCURRENCY = 2`）。
4. **覆盖审计**：一次 `AUDIT_KNOWLEDGE_MAP` 调用（思考模式 + low、输出上限 24,000 token、总超时 180 秒），把**全部**提取结果整包 JSON 化发给模型，返回合并谱系后由代码组装最终知识地图。
5. **首问**：一次 `CREATE_FIRST_QUESTION`（30 秒超时、1,500 token），之后才打开第一个主题、Vita 发出第一句话。

全程受两个绝对截止时间约束（`src/config/agent-limits.ts`）：模型处理合计 **4 分钟**、从读取到首次对话 **5 分钟**。超时即把任务标记失败（保留原文件可重试）。

## 实测数据（真实 deepseek-v4-flash，2026-08 生产构建）

三档合成英文材料走完整 UI 流程（`e2e/phase15-performance-real.spec.ts`，重复段落、低冗余度低）：

| 材料    | 分块  | 提取                | 审计   | 首问 | 结果                                                        |
| ------- | ----- | ------------------- | ------ | ---- | ----------------------------------------------------------- |
| 10 KiB  | 1 块  | 6.0s                | 37.6s  | 1.0s | 通过，模型合计约 45s                                        |
| 50 KiB  | 4 块  | 4 块各 4–6s（2 轮） | 90.1s  | 1.3s | 通过，模型合计约 106s                                       |
| 200 KiB | 14 块 | 前 12 块各 3–9s     | 未到达 | —    | **第 13 块 3 次结构校验失败（约 9s 内耗尽），整个上传失败** |

定向 API 级测量（真实中文学习笔记）：

| 材料                                      | 提取      | 审计                                  | 首问 |
| ----------------------------------------- | --------- | ------------------------------------- | ---- |
| 中文 7KB（2,516 字，1 块，输出 26 条目）  | 31.3s     | 71.5s（2 块量级）/ 85.8s（14 块量级） | 1.0s |
| 中文 15KB（5,311 字，1 块，输出 30 条目） | **77.7s** | **113.3s**                            | 2.1s |

结论：

1. **审计是最大单项耗时**（37–113s，占总量 50–65%），思考模式 + 随地图规模增长；首问开销可忽略（1–2s）。
2. **提取耗时随内容密度陡增**：2.5k 字 31s → 5.3k 字 78s。满 15,000 字符的中文块几乎必然超过单操作 90 秒超时 → 重试 → 失败。当前 15k 字符分块对中文偏大。
3. **4 分钟模型预算的悬崖位置对密度/语言高度敏感，不是固定"2 块必超时"**：密集中文 1 块（15KB）实测 ≈ 193s，2 块以上即可能超时；而稀疏英文合成材料 200KiB（约 14 块）在 Codex 复测中 160.6s 通过、我首测中 4 块 90.1s 审计通过。两者并不矛盾——超时风险随"每块产出的条目数与审计规模"而非"文件字节数"上升。原文"2 块以上几乎必超时"仅对密集中文成立，已降级为风险假设。
4. **健壮性缺陷（独立于超时）**：单块输出校验失败 3 次即耗尽重试，整个任务报废，其余已成功的分块全部作废（我首测 200 KiB 中 1/14 块拖垮全局，失败字段 `knowledgeItems.0.commonMisconceptions.0`；Codex 复测同一用例通过，证明是偶发而非必然）。
5. 合成英文材料显著快于真实中文材料（冗余段落、条目少），仓库内性能数字会系统性好于用户真实感受。
6. **跑批间方差大**：同一 10 KiB 合成用例，我测得模型合计约 45s（审计 37.6s），Codex 测得端到端 10.7s（审计 7.0s），相差约 4 倍。可能来源是 DeepSeek 服务端负载/缓存。这意味着架构必须耐受慢端，不能用快端采样定验收目标。

## 根因

### 问题 1：小文件也要等几分钟

- 即使 10KB 文本（约 3,400 汉字，仅 1 个分块）也要**串行等 3 次模型调用**：提取（几十秒）→ 审计（思考模式，几十秒到 3 分钟）→ 首问。模型逐 token 生成几千 token 的 JSON 是物理耗时，无法靠本地优化。
- 3 次调用顺序有严格依赖：首问依赖审计结果，审计依赖全部提取结果，所以没有并行空间。
- 理论上单块材料最坏可到 90 + 180 + 30 = 300 秒，已超过 240 秒的模型预算——**预算连"最坏情况下的最小文件"都盖不住**。
- OCR 路径另算：扫描 PDF/图片在浏览器 CPU 上跑 Tesseract，每页中文可 10–60 秒，50 页上限纯 OCR 就能吃掉 5 分钟总预算，还没到模型处理就已超时。

### 问题 2：约 10KB 以上几乎必超时

- 分块大小 15,000 字符 ≈ 45KB 中文文本。文件超过约 1 个分块（即 2 块以上）后：
  - 提取变成多轮串行批（每轮 2 块），每轮几十秒到 90 秒；
  - 审计输入随块数增长，思考模式耗时更长、更易触发 24,000 token 输出截断 → 结构修复重试（共享同一 180 秒截止时间，重试只会更紧张）；
  - 4 分钟模型预算在 2 块文件上就非常紧张，3–4 块几乎必然超时 → "整理材料超过 4 分钟，请重试或拆分材料"。
- 大材料的另两道硬边界（均为"高条目密度下"的风险，非按字节必触发）：
  - 审计请求把全部提取结果整包发送，受同源 4MB 请求体上限约束（`AGENT_REQUEST_MAX_BYTES`）。审计请求体 ∝ 提取条目总数而非文件字节数：稀疏英文 200KiB 的审计体仅约 38.5KB（Codex 实测），而我把同一份 26 条目的密集中文提取复制 14 块后审计体即达 253KB。满载 30 万字符的密集中文材料确有逼近 4MB 的可能，属风险假设而非当前瓶颈；
  - 审计输出 24,000 token 上限装不下超大规模材料的全部合并谱系与节点语义，即使时间预算足够也会因截断重试而失败。

### 设计与实现的矛盾

`DESIGN_GUIDE.md` 11.1 承诺单文件 30MB、纯文本 30 万字符、PDF/PPTX 200 页、OCR 50 页；4.2 承诺 5 分钟总预算、提取并行固定 2、审计最多 3 分钟。但按当前"每块一次调用 + 全局审计 + 4 分钟模型预算"的组合，数学上无法达成：

- 30 万字符 → 20 块 → 10 轮串行提取。即使每轮乐观按 40 秒算，仅提取就 400 秒 > 240 秒预算；
- 单次审计（180 秒上限）也装不下 20 块合并谱系的生成时间。

也就是说：**不是设计文档没提大文件，而是当前处理架构的常量组合无法兑现设计承诺**。用户记忆中的"5MB/10MB"在现文档中是 30MB，但同样没被实现兑现。

## 候选方向（按改动量分层，待与 codex 讨论、待用户拍板）

### 第 1 层：健壮性与局部优化（与设计契约无关，建议无论如何都做）

- **单块失败不拖垮全局**：分块提取单块校验失败时按块重试（更大重试次数/间隔），仍失败时保留该块进入审计或降级为参考，而不是整个任务报废（200 KiB 实测的失败模式）；
- **修复提示携带具体约束**：结构修复只给字段路径，模型反复犯同一错误（实测 3 次失败同一字段）；可把该字段的 Zod 约束描述加入修复提示；
- UI 侧已显示分块计数与已用时间；可再明确等待量级但不伪造百分比。

### 第 2 层：改常量，需同步改 DESIGN_GUIDE（中等收益，治"超时"不治"等待"）

- **审计关闭思考模式**（5.2 规定审计用低强度思考；实测审计占总量 50–65%，是最大单项，关掉预计省 30–50%，质量需实测）；
- **中文分块按字节或字数缩块**（实测 5.3k 字提取即 78s，满 15k 字符块必然超时；15k 字符对中文偏大，会增多块数与轮数，需配合并行与预算调整）；
- 提取并行 2 → 3 或 4（4.2 规定固定 2；路由总并发 4，需留对话容量）；
- 模型预算按材料规模弹性化（4.2 规定 4 分钟硬上限）。

### 第 3 层：架构级（根治"等待"，改动最大）

- **A. 流式首问**：首批分块提取完成即打开第一个主题、出首问，剩余分块与全局审计后台继续、知识地图增量可见。体验从"等全量"变成"等 1 块"。需重写 4.2/4.3 流程与任务状态机（处理中任务允许对话、增量持久化、审计完成后替换临时主题等）。
- **B. 合并提取与节点生成**：提取调用同时输出节点草案与四层目标，代码确定性合并，审计降级为轻量去重/可选步骤。单块材料从 3 次调用降到 2 次（实测可省 70–110s 的审计等待）。需改 5.2 两阶段契约、chunkExtraction 契约、审计组装与全部相关测试。
- **C. 仅放宽预算**：把 5/4 分钟上限提高到 10+ 分钟。只解决"稍大就超时"，用户等得更久，与"体验差"诉求相反，不单独采用。

## 待拍板项

1. 是否允许修改 4.2 的"5 分钟 / 并行 2 / 审计 3 分钟"硬指标与 5.2 的"审计用低强度思考"（第 2 层任一改动都涉及）。
2. 是否接受"先聊起来、后台继续整理"的流式产品形态（第 3 层 A），还是坚持"完整整理后再开聊"。
3. 中文分块缩块会增加块数，与 4 分钟预算直接冲突，是否与第 2 层并行/预算调整绑定实施。
4. 扫描 PDF/图片的 OCR 慢是独立问题（浏览器 Tesseract，50 页上限纯 OCR 即超 5 分钟总预算），是否纳入本次。
