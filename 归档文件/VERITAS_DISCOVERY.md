## 一、当前产品定义

### 一句话定义

Veritas 是一款**材料驱动的诊断式学习工具**：它从用户材料中提炼具有诊断价值的知识点，通过苏格拉底式对话判断并补齐理解缺口，最后依据真实对话证据生成学习产物。

### 项目目的

Veritas 首先是一款可以真实使用的学习产品，同时也是产品发起人用于求职展示的 AI 产品作品集。项目不仅要呈现最终界面，还要能够讲清楚产品设计、Agent 机制、评测方法、bad case 迭代和工程治理。

### 当前阶段与下一步

当前唯一重点是把 Veritas 的产品设计与首次开发规格补齐。设计全部确认后，产品发起人会在新窗口开启目标模式，用一晚完成首次开发。

“一晚完成”指在同一个目标模式中连续运行许多轮、许多阶段，直到产品真正完成；不是用一个提示词一次生成所有代码。目标模式可以先搭框架，再实现核心链路、UI、卡皮巴拉、测试和文档，中间不需要产品发起人反复创建新任务或重新下指令。

第一版目标是完整、正式、达到后续可上线质量的本地版本，而不是只演示核心路径的原型。已经提出的核心功能、按钮和交互都需要实现，包括语音、分享、诊断报告、移动端适配和历史记录恢复。当前目标模式只负责本地运行、生产构建和真实浏览器验收，公网部署后续单独处理。没有明确提出、且对项目核心价值没有直接帮助的能力暂不实现。

`BENCHMARK.md` 已降级为稳定版本后的延后事项。当前只保留已有草案，不继续设计评分锚点、黄金案例、bad case 体系或 AI 自动评测，除非它们直接影响核心产品行为。

### 当前核心价值

Veritas 不以快速总结材料或直接回答问题为主要目标。它要帮助用户发现“自己以为懂了、其实没有真正理解”的部分，并在诊断过程中把这些部分学会。

### 目标用户与典型场景

目标用户是：想确认自己是否真正学会材料内容，或希望找出理解盲点的人。

典型场景包括：

- 面试备考；
- 考试复习；
- 资格认证；
- 针对已有材料查漏补缺。

### 输入材料

当前设想支持：

- PPT（仅现代 `.pptx`）
- Word（仅现代 `.docx`）
- Markdown
- TXT
- PDF
- 图片

### 学习结果

对话结束后可以生成：

- 笔记
- 练习题
- 学习评估
- 诊断报告
- 其他参考 Socra 的知识产物

诊断报告应引用用户在对话中的具体回答作为判断依据，并给出下一步学习建议。

## 二、当前核心流程

```text
上传材料
  → 提炼候选知识点
  → 按诊断价值排序
  → 选择若干知识点并拆成独立节点
  → 自动建立默认学习目标，用户可随时调整
  → 用户进入一个或多个节点对话
  → 每个节点依次完成记忆、理解、应用、分析四层诊断
  → 每层内根据回答动态选择追问或提示动作
  → 更新节点进度
  → 生成笔记、练习、评估或诊断报告
```

### 已确认的首次使用流程

- 首次打开网页直接进入主界面，不设置独立欢迎页或新手引导页；
- 材料上传入口位于核心对话区的输入框附近；
- 未上传或未选中材料时，输入区禁用，并通过占位文案提示先上传材料；
- 选择材料后立即创建学习任务；
- 上传、解析、节点生成和失败状态需要清晰反馈；
- 能测量真实进度时显示真实进度，无法测量时使用明确的阶段状态或不定进度，不伪造百分比；
- Agent 1 完成节点生成后，不要求用户确认或手动编辑；
- 默认学习目标不阻塞开始流程；系统先按全面掌握材料建立目标，用户可以在目标卡片或聊天中调整为面试、考试/认证或自定义用途；
- 系统自动进入第一个知识节点并提出记忆层主问题；
- 每个知识节点对应一个独立聊天窗口，四个认知层级共享该节点的聊天记录；
- 用户完成节点的四层后，右侧诊断区明确显示“已完成”；
- 所有任务、节点状态和聊天记录需要持久化并在再次打开时恢复。

## 三、三个 Agent 的当前职责

这里的 Agent 暂时表示产品中的逻辑职责，尚未决定它们是否必须对应三个独立模型调用或三个独立运行进程。

### Agent 1：提炼

职责：

- 读取用户上传的材料；
- 按材料模块提取完整、可追溯的原子知识条目；
- 区分需要深度诊断的核心知识与案例、数据、延伸说明等辅助内容；
- 把 2—5 个高度相关的核心条目聚合为一个诊断主题，独立概念不能为减少数量被强行合并；
- 不设置整份材料最多 8 个节点的总量硬上限；
- 为每个条目记录已进入诊断节点、绑定为辅助内容或仅作参考的明确归属；
- 按核心程度、易混淆程度、迁移价值和前置关系排序诊断主题；
- 自动建立默认学习目标，并允许用户在不阻塞开始流程的情况下随时调整用途。

当前设想中，每个知识节点对应一个独立诊断会话，节点状态互不影响。

### Agent 2：诊断与教学

职责：围绕当前知识节点，既发现用户的理解缺口，也帮助用户真正学会。

已经明确采用固定、逐层递进的认知路径：

```text
记忆 → 理解 → 应用 → 分析
```

四层是每个知识节点都要依次经历的机械流程，不跳层，也不从高层向低层回退。动态适应发生在每一层内部，而不是改变四层顺序。

每层只提出一个主问题。围绕这个主问题可以继续追问、澄清、换角度、举例和搭支架，但不能在同一层偷偷换成另一个新的考察目标。

当前互动原则：

- 每次只推进一个主要问题；
- 优先让用户自己解释、举例、应用和反思；
- 回答正确时给予具体、真诚的鼓励；
- 回答困难时，通过换角度、类比、提示和拆小问题继续引导；
- 不把直接给出答案作为默认行为；
- 主线始终是诊断并教会当前知识点；
- 允许闲聊、吐槽和走神等自然支线出现；
- 在合适时机自然地把对话带回学习主线。

Agent 2 的人格定位是“亦师亦友的学习伙伴”：专业上像家教，态度上像有温度的朋友或哥哥姐姐，而不是机械的答题机器。

### 帮助机制

对话区提供“提示”和“答案”两个明确按钮，但帮助不完全依赖用户主动点击。用户表示“不知道怎么回答”“不知道应该回答什么”时，Agent 2 必须主动澄清回答任务，并在需要时提供带知识线索的帮助。

只有用户主动点击“提示”按钮，才影响最终展示状态并产生“提示后通过”。Agent 2 在普通对话中主动给出的知识线索、案例或类比不改变三种最终状态。

#### 提示

- 提供切入点、思考方向、线索或类比；
- 不直接泄露当前问题的完整答案；
- 使用提示后回答正确，该层仍然通过并获得 25 分；
- 当前层状态记为“提示后通过”；
- 产品在交互和文案上鼓励用户优先使用提示。
- 用户可以多次点击提示；提示力度逐次增强。

#### 答案

- 直接提供当前问题的完整答案；
- 当前层标记为“给答案通过”；
- 当前层获得 0 分，不计为独立通过；
- 展示答案后直接进入下一认知层；
- 产品不鼓励优先使用答案，但不应羞辱或惩罚需要答案的用户。

用户也可能在没有点击答案时连续拒绝回答或持续表示不知道。大约三轮无进展可以作为自动给出完整答案的参考，但不是对所有追问的硬上限；只要用户仍在靠近理解，Agent 2 可以继续引导。具体规则由后续唯一状态机定义。

每层最终只保留三种状态：

- 通过；
- 提示后通过；
- 给答案通过。

不再增加“教学后独立通过”等更细状态。

### 提问必须说明回答任务

Agent 2 不能只问“你怎么理解”“你怎么看”这类范围不明的问题。每个问题都应让用户知道：

- 当前只在考察哪个认知层级；
- 需要回答的是定义、解释、应用还是分析；
- 回答至少覆盖哪些方面；
- 建议用什么长度或结构回答；
- 哪些内容本题暂时不需要展开。

例如，记忆层不应只问：

> “估值分位这个词，你自己怎么理解？”

候选改写方式：

> “这一题只考察基本含义，不需要谈应用。请用一两句话说明：估值分位衡量的是什么，以及 80% 分位表示怎样的相对位置。”

当用户表示不知道该回答什么时，Agent 2 应先区分两种困难：

1. **任务不清楚**：明确回答范围、结构和预期，不提供知识答案；
2. **知识不会**：主动提供例子、类比、关键线索或更小问题，并把后续通过状态记为“提示后通过”。

“澄清回答任务”和“提供知识提示”的边界仍需最终确认。

### Agent 3：产出

职责：读取材料、学习目标和诊断对话，将学习过程整理为指定知识产物。

第一版只实现诊断报告。笔记、练习和其他产物放到稳定版本后的后续迭代。诊断报告自动生成、自动保存，并允许用户下载。

诊断类产物不能只有抽象分数，应尽可能保留以下证据链：

```text
知识目标
  → Agent 提问
  → 用户原始回答摘录
  → 对回答的诊断判断
  → 已掌握内容与理解缺口
  → 下一步学习建议
```

## 四、知识节点与多对话交互

当前设想：

- 一个知识点对应一个独立诊断节点；
- 每个节点拥有独立会话和进度；
- 多个节点像微信中的多个聊天窗口一样并行呈现；
- 用户可以在知识点之间自由切换，进行多头思考；
- 一个节点中的对话状态暂不影响其他节点。

### 1. 左侧：工作区

职责是管理学习任务。每次上传一份材料，就创建一个新的学习任务或“对话窗口”。

当前功能：

- 新建学习任务；
- 展示历史学习任务；
- 搜索；
- 收起或展开边栏；
- 每个任务通过三点菜单进行重命名、置顶、分享和删除。

交互心智参考 DeepSeek 和 Claude 网页版的历史对话列表，但不照搬视觉设计。

### 2. 中间：核心对话区

中间区域内部再分成两部分：

- 左侧为知识节点列表，每个节点类似 PC 版微信中的一个“对话对象”；
- 右侧为当前节点的一对一聊天区域。

用户点击节点后，在聊天区与该节点对应的 Agent 2 独立交流。聊天支持：

- 文字输入；
- 语音输入；
- “提示”按钮；
- “答案”按钮；
- 在多个知识节点会话之间自由切换。

### 3. 右侧：诊断区

实时展示当前知识节点的诊断状态，包括：

- 当前节点名称；
- 记忆、理解、应用、分析四层进度；
- 当前节点得分；
- 当前学习目标；
- 盲点摘要；
- 本次节点列表或其他后续诊断信息。

### 三层导航关系

虽然桌面界面在视觉上可能表现为四列，但产品语义上是三个区域：

```text
学习任务工作区
  → 当前任务的知识节点列表 + 当前节点会话
  → 当前节点的实时诊断
```

## 六、反馈机制的旧版计分提案

> 该 0—100 方案正在被重新评估，不能作为最终开发依据。当前更倾向于取消含义模糊的数字，仅保留材料主题进度、当前四层进度、三种完成状态和自然语言完成总结。

每个知识节点单独计分。四个认知层级各占 25 分，满分 100 分。

| 当前层结果 | 得分 | 状态记录 |
|---|---:|---|
| 独立回答通过 | 25 | 通过 |
| 使用提示后通过 | 25 | 提示后通过 |
| 获得完整答案 | 0 | 给答案通过 |

计分保持简单、透明。提示不扣分，避免用户因担心失分而拒绝寻求有效帮助；给答案通过不计分。

100 分主要表达一个知识节点的学习完成度。每个节点独立拥有 0—100 分，四个层级各占 25 分。“给答案通过”虽然获得 0 分，但该层仍算完成并继续推进。不提供层级或节点重做功能。

## 七、设备与数据

### 设备支持

Veritas 需要同时支持电脑端和手机端。

桌面端采用上述三大区域。手机端无法同时容纳三块区域，具体导航与折叠方式尚待确定。

### 数据保存

当前阶段：

- 上传材料先保存在浏览器本地；
- 学习任务、节点对话与诊断状态也需要支持本地恢复。

后续部署到服务器后：

- 用户再次打开网页时可以看到持久化的历史学习任务；
- 使用体验类似带历史记录的网页对话产品；
- 账号、跨设备同步和服务端存储方案尚待设计。

### 模型与密钥

- 三个 Agent 已确定统一使用 `deepseek-v4-flash`，首版不调用 Pro；
- Agent 2 实时交互显式关闭思考模式；Agent 1 覆盖审计和 Agent 3 报告可以使用 Flash 的低强度思考；
- 具体 API 模型标识与参数需要在开发前依据官方文档核实；
- API Key 不得写入前端代码、浏览器存储、仓库或文档；
- 用户已经将专用开发 Key 放入被 `.gitignore` 排除的 `.env.local`；目标模式需要进行少量真实 API 冒烟测试，但不得读取、输出、记录、截图或提交密钥值；
- 即使材料和历史记录保存在浏览器，本地网页也必须通过服务端代理或受控本地后端调用模型，避免向用户端暴露长期密钥。

## 八、目标对话体验

用户应感觉自己正在电脑或手机上与一位真人家教一对一聊天：

- 可以发语音，也可以打字；
- 对话一步一步推进；
- 允许自然回应、闲聊、吐槽和短暂走神；
- 语气有温度，但专业判断必须具体；
- 固定四层是系统内部的学习骨架，不应让表层对话显得机械；
- 用户在轻松交流中逐渐暴露理解缺口；
- Agent 2 通过引导帮助用户自己想明白并真正学会。

每一轮主线教学回复都必须让用户获得至少一种明确收益：知道自己哪里理解正确、知道具体缺了什么、获得一个新的例子或思考支架，或者知道下一步怎样回答。禁止只说空泛鼓励后继续出题，也禁止连续使用考试口吻、模板化评价和与用户原话无关的机械追问。

## 九、当前认知层级通过标准

| 层级 | 当前通过标准 |
|---|---|
| 记忆 | 能识别概念或说出基本定义 |
| 理解 | 能用自己的话解释，而不只是复述原文 |
| 应用 | 能把概念放进具体场景，并说明如何使用 |
| 分析 | 能拆出机制、因果、边界或对比关系 |

这些标准目前是参考版本，后续需要进一步定义评价证据、模糊回答的处理方式和每层的完成条件。

## 十、待讨论的设计建议

以下均未确认。

### 1. 固定四层与自然对话可以并存

已经确定四层必须机械地逐层推进。这里需要优化的不是层级顺序，而是每层内部的互动：问题数量、追问方式、提示深度和过渡文案都可以动态变化，使固定学习骨架不等于机械聊天。

### 2. Agent 必须在用户不会时主动搭支架

苏格拉底式追问是默认机制，但如果用户连续卡住，持续反问可能产生挫败感。候选策略是：

```text
开放提问
  → 轻提示
  → 换角度或类比
  → 拆成更小问题
  → 提供关键一步
  → 必要时直接讲解
  → 用新问题重新检查是否理解
```

结合当前设计，用户点击“提示”不是获得知识线索的唯一入口。当用户明确表示不会或不知道该回答什么时，Agent 2 也要主动缩小问题、解释作答要求，并在必要时给出例子、类比或知识线索。只要 Agent 实质上提供了知识提示，后续通过就应进入“提示后通过”候选状态，不能因为提示不是按钮触发而漏记。

### 3. “节点独立”可能需要拆成两种状态

节点的题目、消息和完成进度可以彼此独立，但知识点之间可能存在前置关系，同一个用户在不同节点暴露出的能力也可能有迁移价值。候选方案是：

- 保留独立的节点会话状态；
- 另设一个受控的共享学习者画像或证据层；
- 只有明确相关的证据才允许影响其他节点。

是否需要共享层仍待确认。

### 4. 诊断价值需要可解释的排序依据

候选知识点可以考虑按以下因素排序：

- 对整份材料的核心程度；
- 是否是其他知识的前置基础；
- 是否容易产生常见误解；
- 是否适合通过问答暴露真实理解；
- 是否能迁移到应用场景；
- 材料中是否有足够证据支持可靠诊断。

### 5. 知识节点应保留材料依据

每个节点除名称和目标外，可以绑定来源页码、段落或图片区域。这样 Agent 2 的判断与 Agent 3 的报告都能追溯到用户上传的材料，减少脱离材料自由发挥的风险。

### 6. 分数必须和三种状态同时呈现

提示后通过与通过都得到 25 分，有利于鼓励求助，但两者代表的过程不同。界面和报告不能只显示总分，还应同时显示每层的“通过 / 提示后通过 / 给答案通过”状态。

不引入“教学后独立通过”等额外展示状态，保持产品语言简单。

## 十一、当前关键张力

- **完整诊断 vs. 对话效率**：逐层检查更完整，但可能过慢。
- **苏格拉底式引导 vs. 及时教学**：坚持不说答案可能妨碍真正学会。
- **节点独立 vs. 知识关联**：完全隔离简单清楚，但可能丢失前置关系和迁移证据。
- **多窗口自由切换 vs. 注意力碎片化**：并行能支持多头思考，也可能让学习主线变散。
- **人格温度 vs. 诊断可靠性**：自然陪伴很重要，但不能用空泛鼓励掩盖判断依据。
- **固定四层流程 vs. 真人聊天感**：后台顺序必须固定，前台语言和追问不能像考试表单。
- **同分结果 vs. 不同帮助程度**：提示后通过与通过同为 25 分，必须依靠三种状态标签解释差异。
- **主动搭支架 vs. 计分一致性**：Agent 自动给知识线索时，也必须可靠地进入“提示后通过”路径。
- **桌面多栏信息密度 vs. 手机单屏限制**：桌面结构清楚，但移动端需要重新组织导航，不能直接压缩三栏。

## 十二、视觉与品牌方向

### 设计语言

目标是形成有美感、有个人风格、精致且能够长期扩展的视觉系统。

当前偏好：

- 整体美术风格偏向多邻国式的亲和、活泼与完成感：柔和大圆角、粗线条描边、几何化图形、大量留白、鲜明反馈、触感动效、插画参与和克制的孟菲斯式点线面装饰；

- 不复制多邻国的具体配色、组件造型、字体、图标或页面；
- 核心对话的信息架构参考 PC 版微信的“对象列表 + 单聊窗口”，不复制微信的具体视觉样式；
- 卡皮巴拉插画参考图：`references/mascot-style-reference.jpg`；
- PC 微信布局参考图：`references/pc-wechat-layout-reference.png`；
- 早期 Veritas 信息架构草图：`references/early-layout-draft.png`。

参考插画只用于研究圆润轮廓、亲和力、表情扩展和品牌 IP 的应用方式。卡皮巴拉必须拥有原创的轮廓、配色、服饰、道具和性格设定，不能只把参考角色替换成另一个动物。

### 卡皮巴拉的角色方向

存在两个候选方向：

1. 每个知识节点拥有不同家教形象；
2. 只有一个贯穿产品始终的卡皮巴拉学习伙伴或品牌吉祥物，类似统一品牌角色。

当前更倾向第二种。候选职责包括：

- 引导上传材料和创建任务；
- 解释产品如何使用；
- 在空状态、加载、成功、卡住和完成时提供反馈；
- 出现在进度、报告和品牌传播中；
- 通过不同表情、姿势和少量配件表达状态，而不是为每个节点创造新角色。

候选名字尚未确认。当前建议优先考虑与 Veritas 有联系、两到三个音节、中文和英文都容易称呼的名字，例如“维塔”。

## 十四、工程治理原则

### 已知痛点

- AI 自作主张增加抽象、配置和未来预留，造成代码漂移；
- 模块耦合，局部修改产生连锁破坏；
- 早期遗留和未使用代码长期干扰后续开发；
- AI 的说明与实际代码可能不一致；
- 针对每个 bad case 打补丁，导致规则过拟合且无法泛化。

### 当前原则

- KISS：能用简单代码解决，不引入多余层级；
- YAGNI：不实现当前没有明确需求的能力；
- 单一职责：每个模块只承担一种可清楚描述的职责；
- 确定性优先：状态流转、计分、权限、数据校验、持久化和 UI 显隐由代码控制；
- 语义判断才交给模型：知识提炼、回答理解、自然追问、教学提示和报告生成由 Agent 处理；
- 模型输出必须经过结构化 schema 校验，不能让自由文本直接修改核心状态；
- 先修复产生一类问题的协议、状态机或边界，再考虑单个 case 补丁；
- 保留 TDD：确定性行为由自动化测试锁定，Agent 语义质量由 benchmark 评测；
- 每次修改后检查真实 diff、运行相关测试，并清理本次确认已经无用的代码；
- 不允许为了“以后可能用到”留下未接入的抽象、配置或兼容层。

### 安全是首版基础约束

虽然当前只要求本地运行，首版仍必须按照未来存在真实公网用户和恶意输入的条件设计，不能把安全推迟到部署阶段：

- 上传文件、文件名、MIME、压缩内容、解析文本、用户消息和模型输出一律视为不可信输入；
- 组合校验文件扩展名、MIME、文件签名、压缩后体积、压缩比、条目数、页数、像素和文本长度；
- 不执行文档宏、脚本、外部链接或文档中的自然语言指令，只提取受限纯文本与图片像素；
- 材料内容与系统指令在模型上下文中严格分隔，材料中的“忽略此前规则”等内容只能被视为学习材料；
- 运行时 Agent 不拥有执行代码、读取环境变量、访问其他任务、调用任意工具或请求任意网址的权限；
- API Key 只由受控后端读取，不进入前端、IndexedDB、源码、文档、聊天、测试快照或日志；
- 所有 API 输入和模型结构化输出都通过 schema 校验，状态变化由代码授权；
- 用户内容和模型 Markdown 必须转义或按严格白名单清理，禁止直接注入 HTML；
- 设置请求大小、频率、并发、超时、输出 token 和重试上限，并使用 CSP 等安全响应头；
- 自动化测试必须包含提示注入、XSS、伪造类型、畸形压缩包、资源耗尽和非法状态转移案例。

## 十五、首次开发前决策清单

以下问题按优先级排列。P0 未解决前不能开启目标模式；P1 应在开发说明形成前确认；P2 可以明确延后。

产品发起人已授权由 Codex 对 P1 项目作出完整设计判断；这些决定仍需记录到最终规格，但不要求产品发起人逐项提出方案。

### P0：阻塞开工的产品决策

#### 1. 首次开发的范围边界

- “一晚完成”的版本必须包含哪些能力；
- 哪些能力允许使用简化实现；
- 哪些材料格式首版真实支持；
- 语音、分享、报告、移动端和历史记录哪些必须真实可用；
- 哪些功能明确列入 Not Doing，防止目标模式擅自扩展。

#### 2. 完整主流程与页面状态

- 用户从第一次打开页面到完成一个节点的完整步骤；
- 上传前、上传中、解析中、解析失败、节点确认、诊断中、节点完成和任务完成分别显示什么；
- 材料上传后是否必须先确认节点，还是自动进入第一个节点；
- 用户离开后再次打开，恢复到哪个任务、节点和认知层级；
- 整个任务在什么条件下算完成。

#### 3. Agent 1 的可执行协议

- 一份材料默认提取多少节点，是否设置上下限；
- 知识节点的最小与最大粒度；
- “诊断价值”的排序因素和优先级；
- 是否识别节点之间的前置关系；
- 节点是否必须绑定材料页码、段落或图片位置；
- 用户能否重命名、删除、补充、合并、拆分和重新生成节点；
- 材料信息不足、解析失败或没有高价值节点时怎么办；
- Agent 1 的结构化输出 schema 与完成条件。

#### 4. Agent 2 的问题协议与状态机

- 四层中每层默认提出一个主问题还是允许多个问题；
- 每层最多追问多少轮，怎样避免无限循环；
- “通过”的判定门槛，部分正确时如何处理；
- 用户答错、答非所问、回答过短、复制材料、表示不知道或出现误解时分别走什么动作；
- 澄清作答要求与提供知识提示的边界；
- Agent 主动给出知识线索时，是否自动记为“提示后通过”路径；
- 点击提示后可以给几次提示，提示是否逐步增强；
- 点击答案后的完整回复格式，以及何时进入下一层；
- 用户闲聊、吐槽或切换节点后，怎样保留并恢复当前问题；
- Agent 2 的结构化输出 schema，模型能决定什么、代码必须决定什么；
- 当前层、帮助状态、分数和下一动作的唯一状态机定义。

#### 5. 计分与完成语义

- 100 分表达掌握程度、独立完成度还是学习完成度；
- “通过 / 提示后通过 / 给答案通过”在诊断区分别如何显示；
- 0 分的层级是否仍标记完成；
- 一个节点四层结束后如何总结；
- 一个任务包含多个节点时，是否显示总分或总体进度；
- 是否允许重做某一层或整个节点，重做后如何计分。

#### 6. Agent 3 的首版产物

- 首版必须提供哪一种产物；
- 诊断报告是节点级还是任务级；
- 报告由用户主动生成还是任务完成后自动生成；
- 报告的固定章节和必填证据；
- 用户原话引用到什么粒度；
- 笔记、练习、评估等其他产物是否首版实现；
- 产物是网页查看、复制、Markdown 下载还是其他形式。

#### 7. 数据与材料边界

- 首版材料、解析文本、任务、节点、消息和报告分别保存在哪里；
- 浏览器本地使用 IndexedDB、文件句柄还是其他方式；
- 原始材料是否发送到服务端，还是只发送解析后的文本；
- 用户上传材料时如何说明数据会被发送给模型；
- 单文件还是多文件，每个任务允许多少材料；
- 文件大小、页数、图片数量和文本长度上限；
- 删除任务时需要删除哪些本地数据；
- 首版是否没有账号与跨设备同步，服务器持久化明确延后。

#### 8. 技术栈与模型调用

- 前端框架、语言、样式方案和状态管理；
- 服务端或本地受控后端采用什么方案；
- PDF、DOCX、PPTX、Markdown、TXT 和图片分别用什么解析方式；
- 图片与扫描 PDF 是否需要 OCR；
- DeepSeek V4 的准确 API 模型标识、参数和返回格式；
- Flash 与 Pro 的调用分工；
- 是否流式返回对话；
- API 失败、限流、超时和结构化输出不合法时如何重试与提示；
- `.env`、密钥代理和日志脱敏规则。

#### 9. 首次开发的验收标准

- 至少一条端到端黄金路径的具体材料与预期结果；
- 哪些功能必须通过自动化测试；
- 哪些交互必须用真实浏览器验证；
- PC 与手机各使用什么视口验收；
- 构建、类型检查、测试和启动命令；
- 什么状态才允许宣布 Veritas 首版完成；
- 是否要求部署，以及部署目标。

### P1：应在开发说明形成前确认

#### 10. 桌面端交互细节

- 三个区域的默认宽度、最小宽度和可收起规则；
- 工作区搜索、置顶、重命名、分享、删除的具体行为；

#### 11. 手机端信息架构

#### 12. 语音输入

#### 13. 视觉设计系统

- 空状态、加载、成功、错误和完成状态的画面；

#### 14. 卡皮巴拉品牌角色

- 是否正式采用“单一学习伙伴/吉祥物”方向；
- 角色名字；
- 性格关键词、语气和不能出现的行为；

- 首版需要哪些表情和姿势；
- 吉祥物是否出现在聊天头像中，还是只负责产品引导和反馈；
